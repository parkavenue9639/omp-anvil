# Subagent Coordination

仅作用于顶层 OMP 会话。`task` 工具描述中的 `# Inputs` 与 `# Available Agents` 已实时注入每个预设的工具权限、只读/阻塞标记和 `@role` 绑定；本指南聚焦**经济性权衡、角色真实优劣势、异步协作规范与决策范式**，不复述参数表、具体模型名，也不混入任何特定仓库规则。

## 1. 上下文经济学：内联 vs. 委派

| 执行方式 | 核心优势 | 主要成本与风险 |
|---|---|---|
| **主会话直接内联** | 零交接损耗；保有完整历史意图与决策前后文；无契约误解风险 | 上下文随轮次膨胀，后期每多一次探索、试错或周边编辑都在更厚的缓存上下文上计费；大面积检索噪音永久留在主上下文中 |
| **子 Agent 委派** | 干净短上下文起步；检索噪音与试错过程随返回自动丢弃；多独立切片可并发缩短墙钟耗时 | 需要派前定缝（边界、契约、错误模型）、传递关键背景并由主控整合与终验；跨切片耦合过紧时易返工 |

由上述代价结构直接导出两条工作纪律（无需套用死板的文件数阈值）：

- **小范围或强耦合改动直接内联**：改法已经明确、局部修改步数少、或几处改动高度互相依赖时，走内联总成本显著更低；不为了凑并行度或套模板强行派发。
- **一旦进入并行委派，主控保持薄编排位**：当工作体量与独立性足以覆盖定缝成本时，把**全部独立实现切片**（包括边缘小修与对应单元测试）按清晰且互不相交的文件所有权一次性分派给合适预设。并行子 Agent 启动后，主控只保留薄集成入口接线、环境只读确认与最终统一门禁，原则上立即 `wait` 等待收敛——避免主控背着最厚的主上下文一边同步改大量实现/测试，一边陷入“父子或兄弟同改一文、边集成边热改契约”的双重浪费。

## 2. 全谱系子 Agent 真实优劣势画像

选角遵循**问题开放度 × 内部机制复杂度 × 作用表面 × 延迟/配额成本**三维权衡，绝不将异构任务留空全部推给默认 `task`：

1. **只读侦察：`scout`**
   - **优势**：吞吐快、只读零写风险，最适合在大片未知代码库、配置链或外部文档中隔离原始检索噪音，替主会话省掉大量 `read`/`grep` 上下文。
   - **劣势**：无写入权限且多一次交接往返。**若目标文件与改法已经明确，或读完立即要改同一位置**，直接交给对应写预设连读带改更连贯。
2. **通用实现四档：`fast` / `routine` / `task` / `engineer`**
   - **`fast`**：延迟最低、配额成本接近于零。问题空间完全收敛时（根因与定位明确的点位修复、导入/类型/常量同步、既有小功能微调、确定性断言补充）产出比最高；**劣势**是开放式设计与深层跨模块不变量推演能力弱，输入边界越清楚发挥越稳。
   - **`routine`**：按规范与范式落地的性价比极高、配额温和。对外契约或仓库样板已确定、但代码体量或规则细则较多的成块工作（配置解析与校验、Schema/DTO 映射、标准脚本/部署接线、按既有套路成批写单元测试）首选 `routine`——既避免了 `fast` 处理中等规则体量时的浅层上限，也避免了 `task` 面对“已锁死规格”时做过多防御性全局阅读；**劣势**是不适合设计复杂并发协议或排查未知故障。
   - **`task`（默认）**：自主查证与代码组织最均衡，适合“目标与外部边界清晰、但切片内部结构仍需适当查证才能收敛”的标准业务功能模块；**劣势**是对已完全定型的模式化切片容易多绕几轮保守探索与长思考（不如 `routine`/`fast` 干脆），对极端高风险系统机制又不如 `engineer` 稳妥——因此只把真正“标准且尚有局部探索空间”的切片留空或显式给 `task`。
   - **`engineer`**：最强深度推理与系统边界把控力。只要切片**内部**存在复杂状态空间——并发同步与锁、幂等/重试/退避与取消生命周期、失败补偿、棘手状态机恢复，或根因未知的疑难故障——**即便外部接口契约已完全冻结，也应显式指定 `engineer` 争取一次做对**；**劣势**是占用珍贵主力高阶配额，用在常规或样板切片上收益为负。
3. **前端与视觉表面：`frontend-engineer` / `visual-edit` / `visual`**
   - **`frontend-engineer`**：自动预载前端工程规范与工具技能，擅长有界组件架构、交互状态流转、无障碍与响应式实现；**劣势**是技能上下文相对较重，若只是改几行文案、常量或现成属性对齐用 `fast` 更省，跨前后端的协议/类型语义仍须先在父级定好契约。
   - **`visual-edit` 与 `visual`**：`visual` 只针对截图/设计稿/视频帧等冻结视觉资产做像素级只读挑刺，不改代码也不臆测不可见交互；`visual-edit` 根据明确视觉偏差与既有设计 token 做局部样式与排版修复，若偏差源自复杂状态机或 API 数据契约则退回给工程预设。实时有状态表面（真实浏览器、终端、桌面窗口）的交互验证始终由主会话持有。
4. **发散创意与深度收敛：`creative` / `deep`**
   - **`creative`**（低频只读）：用于全新产品特性、创新交互范式或明确需要差异化方案发散的前置探索，产出实质不同的方向并附最廉价的证伪实验；不负责写代码或做工程收敛，常规功能加塞 `creative` 只会制造冗余噪音。
   - **`deep`**（只读分析与裁决）：适合真正的架构分叉权衡、跨边界契约张力梳理或复杂根因假设推演，不受当前实现惯性偏见影响；**劣势**是单次深度推理代价高，冻结契约内常规工程细节由主控直接拍板，能读几眼代码直接看清的事实更不应上 `deep`。
5. **独立对抗挑战：`review` / `security`**
   - **优势**：拥有干净且不继承实现者心理预设的上下文，最擅长针对已成型交付主动找主路径反例与不变量破坏（`review`），或专门审计权限边界、信任链与攻击路径（`security`）。
   - **劣势**：重推理成本高。多切片或常规改动只要主控自己核对契约并跑通确定性测试就够了；**仅当变更后果重、机制复杂或用户要求独立把关，且外部流程尚未覆盖同类干净审查时**才按需调用（有明确功能缺陷才需要各自聚焦，不要用相同 prompt 重复堆砌多个审校）。

## 3. 契约完备性、局部快反馈与异步督导

- **派前定缝与零拷贝交接**：并行派发会写文件的子 Agent 前，主控先冻结三要素：① 互不重叠的文件/目录所有权；② 共享接口、导出签名与**跨模块错误类/区分码/事件字段**（缺错误契约是最常见的中途返工源）；③ 聚焦阅读边界与定向验证期待。共用的大段规范、设计摘录和上下文只写一份到 `local://<path>`，下游统一经 `local://` 或前序 `agent://<id>` 引用，不在多轮之间整段复述粘贴；当契约已自洽时，明确告诉子 Agent 需要对齐的周边目录，提示不必全仓漫游。
- **区分散快反馈与共享重门禁**：完全剥夺子 Agent 的任何验证手段，会逼迫谨慎模型通过大面积读代码“脑测”空转；相反，让多个并行子 Agent 各自运行全仓构建或全局代码生成又会踩踏共享产物。原则上**放行不冲突的轻量局部反馈**（如无语言服务冲突时的 `lsp` 诊断，或指向己方独占测试文件的单测自验），把工作区级构建、共享生成、全局格式化与有状态集成测试统一收归主控在收敛后跑一次。
- **按确定性与工作区约束精细控参**：
  - `effort`：仅在目标、位置与步骤全部封闭且不靠深度推理即可收敛时传 `"lo"` 或 `"med"`；开放调查、复杂架构、系统攻坚与审校保留省略以沿用角色默认高档位。
  - `Stop-if`：用具体上报条件代替死板步数上限（如：基线前提被证伪、发现冻结契约冲突、必须修改己方所有权外文件，或同一阻塞重试无新证据时立即携带已有事实返回）。
  - `cwd` 与 `isolated`：已有独立目录或同仓兄弟 git worktree 时直接在 `tasks[].cwd`（或 `eval` `agent({ cwd })`）绑定对应路径（二者互斥）；共享检出中读任务与文件正交切片无需克隆，仅当多路并行写会污染邻近文件或共享编译/生成物才显式传 `isolated: true`。常规并行用批处理 `task`；大批量同构批处理或跨轮复用的 `Author <-> Verifier` 循环才用 `eval` `agent()`/`workpool()`。
- **异步在途督导与配额容错**：长耗时任务按 `read proc://<id>` 观察到的**实际有效进展**（而非单纯请求计数）判断是否卡死；发现轻度偏航时直接 `write agent://<id>` 热纠偏（向多名在途成员广播同一裁决时，先写入 `local://<path>` 并在同一回合并行发出全部 `write agent://<id>`）；兄弟切片间仅涉窄接口对齐时在 brief 中给出对端名字，令其直接点对点 `write agent://<PeerName>` 对齐；真正零进展死循环或所属分支作废再 `write proc://<id>/kill` 止损。遇到模型配额耗尽（`429` / `RESOURCE_EXHAUSTED`）时，禁止原样死磕重试或空转等待，立即切换同能力目录中尚有余量的其他预设重试一次，或在剩余尾巴清晰有限时由主控内联收口。
- **集成与返修归属**：收回结果暴露出定位和确切改法都已一目了然的局部疏漏（对齐导入导出、补齐夹具前置、按确切行号调整一两处参数）时，主控直接内联修好重验比发消息转述更快；只有涉及未查明切片内部逻辑、依赖子 Agent 深度局部上下文或会与其在途改动冲突时才打回原负责人；原会话已被多轮纠错污染或进入全新阶段时重开新会话。

## 4. 通用委派策略 Few-Shot（场景 → 权衡 → 策略）

以下范式仅展示“如何算账与选角色”，实际执行结合现场信号动态调整，不机械照搬名额：

1. **场景 A：局部紧耦合修补（纯主控内联）**
   - *情形*：已定位问题集中在 2–3 个互相紧耦合的文件（如改接口入参并顺带更新唯一调用方和断言），总修改量几十行。
   - *权衡*：写 seam + 派发 + 集成验收的沟通成本高于直接修改，切开还会人为制造跨边界对齐成本。
   - *策略*：**0 子 Agent**，主会话直接一次性读完相关区间、改代码、跑受影响验证闭环。

2. **场景 B：大仓陌生链路调研后再定去留（先 `scout` 降噪，再按体量内联或派写）**
   - *情形*：只知道表面症状（如某配置项在运行期未生效），不清楚跨多少模块传递。
   - *权衡*：直接让臃肿的主上下文做几轮全仓 `grep`/`read` 会把海量噪音永久写进主缓存，但还没摸清文件归属前直接派写手又容易改偏。
   - *策略*：先派 1–2 路并发 `scout` 按模块方向精准查出调用链、涉及文件与配置优先级；收回确定事实与精确文件列表后，若改动很小则主控直接内联修掉，若发现是独立中大模块再无缝切换到对应写预设。

3. **场景 C：复合任务异构并行落地（薄主控定缝 + 四档与专科协同 + `wait`）**
   - *情形*：需要一次性交付“结构化配置加载与校验 + 带并发槽位控制与重连退避的运行时 + 前端管理面板组件与交互状态 + 两处旧入口简单参数同步”。
   - *权衡*：把全套逻辑压进主控会反复刷新高缓存成本；全留空走默认 `task` 又会让配置和同步点白耗慢思考额度，或让普通预设在并发退避边界踩坑；若主控自己还兼写大块周边实现，容易在中途改契约导致返工。
   - *策略*：主控先把接口签名、错误类与每路互不重叠的文件清单冻结写入 `local://seams.md`，同一批 `task({ tasks: [...] })` 并行派出——**配置解析与单测**指派 `routine`，**并发槽位与重试状态机**显式指派 `engineer`，**前端面板组件**指派 `frontend-engineer`，**两处明确调用点对齐**指派 `fast`（`effort: "lo"`）；派发后主控即刻 `wait`，全部收回后主控仅做根入口装配与全局集成测试验证。

4. **场景 D：开放式产品创意或两难架构分叉（先只读发散/收敛，再冻结开写）**
   - *情形*：接到高度开放的新产品/交互方向探索（尚无明确形态），或实现前发现两种数据流/状态模型各有硬伤。
   - *权衡*：未收敛方向直接派并发实现大概率全盘推翻；用强推理写角色边试边改代码是最高成本的探索。
   - *策略*：全新探索期先单派 `creative` 给出少量差异化方案与最廉价的证伪点，或当方案已收敛到 2 个具体工程取舍时单派 `deep` 做无偏架构对比；由主控吸收证据拍板冻结单一方向后，再派工程预设编码。

5. **场景 E：高后果核心变更的分层收口（实现与独立挑战分离）**
   - *情形*：改动涉及多租户隔离边界、权限模型、资金/账本一致性，或复杂多端可视化改版，且当前项目尚未有外部强独立审查关卡覆盖同类风险。
   - *权衡*：实现者在多次调试后容易对自己的边界假设产生盲区，但让普通杂活每单都附加一次重型审查又太贵。
   - *策略*：先让实现预设落盘并过基础自验，再视具体风险面**精准单派**一位干净上下文挑刺者——信任边界与权限变更派 `security`，关键并发/不变量改写派 `review`，携带冻结渲染截图的界面交付派 `visual`（若需按截图修像素偏差则切 `visual-edit`）。主控核实其反馈：确定性小漏点直接内联补齐，涉及切片设计错误才退回原实现者。
